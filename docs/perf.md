# VLM 呼叫效能優化報告

比較對象：
- **baseline**：優化前設定（整張畫面 1280 寬、預設 JPEG 品質、沒有 `think`/`num_ctx`/`num_predict` 欄位，讓 Ollama 用模型預設行為）
- **optimized**：本次優化後設定（整張畫面縮到 768 寬／JPEG 品質 80、`think:false`、`num_ctx:4096`、`num_predict:200`、`temperature:0`、本機 phash 去重、4 頻道並行）

模型：Colab 上的 `gemma4:12b`（vision 能力）。所有即時測試都在同一個 Colab session 上完成，網路環境相同。

## 1. 摘要

| 指標 | baseline | optimized | 變化 |
|---|---|---|---|
| 平均每筆耗時（只算成功的） | 29.1 秒 | 2.95 秒 | **快約 9.9 倍** |
| 平均每筆耗時（含失敗重試的實際成本） | 46.6 秒（13樣本估）／55.4 秒（CTS 8筆實測） | 3.12 秒（CTS 62筆實測） | **快約 15–18 倍** |
| 成功率（3 次重試後） | 8/13 = 61.5%（混合樣本）；7/8 = 87.5%（CTS 參考） | 60/61 = 98.4%（CTS 62筆，扣掉1筆本機去重沿用） | 明顯更穩定 |
| 目標：5 秒內 | ✗ 達不到 | ✓ 達到（2.45s–3.60s，CTS 62筆最慢 3.59s） | 達標 |

**結論**：目標「5 秒內、總筆數減半」—— 單筆延遲已達標（平均 ~3 秒，遠低於 5 秒門檻）；總筆數減半主要靠「本機去重」，但這個時段（台股崩盤密集快報）實測去重空間有限（詳見第 4 節），真正讓總時間大幅下降的是**單筆速度**跟**4 頻道並行**，不是筆數減少本身。

## 2. 耗時拆解（哪裡花掉時間）

每筆都記錄到 `out/logs/vlm_timing.jsonl`，欄位：`wall_seconds`、`total_duration_s`、`load_duration_s`、`prompt_eval_count`、`prompt_eval_duration_s`、`eval_count`、`eval_duration_s`。

| 階段 | baseline（平均） | optimized（平均） | 說明 |
|---|---|---|---|
| `load_duration_s` | 0.6–2.1s | 0.17–0.34s | 模型已暖機，差異主因是 optimized 請求體更小 |
| `prompt_eval_count`（輸入 token） | ~1054–1078 | ~790–814 | 768 寬圖片的視覺 token 數變少 |
| `prompt_eval_duration_s` | ~0.43–0.90s | ~0.43–0.86s | 差異不大，這段本來就快 |
| `eval_count`（輸出 token） | **368–2525**（常常上千） | **34–67** | **這是耗時的主因** |
| `eval_duration_s` | 5.5–38.9s | 0.43–1.69s | 幾乎跟 eval_count 成正比 |

**關鍵發現：baseline 沒關閉 `think`，gemma4 的「思考模式」會先生成一大段思考過程（有時超過 2000 個 token），耗時幾乎全部花在這裡；`eval_duration_s` 經常佔 `total_duration_s` 的 90% 以上。更糟的是，有時思考過程會把整個生成預算用完，導致最終實際輸出是空字串，`message.content` 解析失敗，整個請求算失敗要重試。**

## 4. 本機去重效果（不打網路，純 phash 比對）

用 `python src/vlm.py --estimate-only` 量測（全小時資料，4 台）：

| 台 | 原本筆數 | 去重後需呼叫 | 省下 |
|---|---|---|---|
| ftv | 341 | 335 | 6（1.8%） |
| tvbs | 424 | 418 | 6（1.4%） |
| ebc | 450 | 446 | 4（0.9%） |
| cts | 420 | 417 | 3（0.7%） |

**老實說效果不大**。原因：這個時段剛好是台股大崩盤的高頻率新聞快報，分析發現心跳幀之間（每30秒）畫面內容距離大多落在 22–38（滿版 64），代表畫面本身幾乎每次取樣都真的在變（移動的人、換鏡頭），能判定為「跟上次一樣不用問」的情況很少；事件之間的距離更是本來就 ≥20（因為 `detect.py` 自己用門檻 20 判定出來的事件，相鄰事件差距必然超過這個門檻，殘留重複本來就只會卡在邊界值附近）。這個去重機制邏輯正確、也確實省下了幾筆，但在「高頻率換標題」的新聞時段天花板很低；在比較平靜、廣告或長時間同一畫面的時段應該會有感很多。

## 5. CTS 前 10 分鐘實測（真實規模）

CTS 影片 00:00–10:00 共有 **62 筆**（42 事件 + 20 心跳）。原始資料：`out/logs/cts_first10min_events.jsonl`，結果：`out/logs/cts_bench_optimized.jsonl` / `out/logs/cts_bench_baseline.jsonl`。

### optimized（62 筆全部跑完）

- 本機去重：61 筆需要真的呼叫、1 筆沿用（省下的那 1 筆）

- 平均每筆 **3.12 秒**（最快 2.64s、最慢 3.59s）
- 62 筆總耗時：**207 秒（約 3.5 分鐘）**

## 6. 失敗案例調查

### optimized 裡唯一的失敗：cts event@331（12:05:31）

**不是逾時，也不是 JSON 格式錯誤** —— 是 Ollama 伺服器直接回 **HTTP 500 Internal Server Error**，而且連續 3 次重試都是同樣的 500，每次只花 3–4 秒（代表伺服器很快就打回票，不是卡住在生成）。

**事後單獨重跑這張圖，仍然是 500**（不是暫時性問題，是這組輸入每次都會讓伺服器出錯）。檢查過圖片本身：`event_00331.jpg`（1280x720）跟 `event_00331_crop.jpg`（282x79）都能正常讀取、內容是一般的記者會畫面，肉眼看不出異常。根本原因無法從客戶端判斷（可能是 Colab 那端某種資源狀態或這張圖片編碼後的某個邊界情況讓模型端處理出錯），需要有伺服器端日誌才能進一步定位。目前的重試機制會正確地重試 3 次後放棄並記錄失敗，不會卡住整批任務，這點符合預期。

### baseline 的 2 個失敗（cts@210 重試3次後失敗；13樣本裡另外 5 個也是同類狀況）

確認是**空輸出**（`message.content` 為空字串 → JSON 解析失敗），根源是前述的「思考模式耗盡生成預算」，不是連線問題。這個失敗模式在 optimized（`think:false`）設定下完全沒再出現過（13+62=75 次呼叫裡 0 次這種失敗），印證了關閉思考模式不只是加速，也是修正穩定性的關鍵。

## 7. 四台整小時推算

全小時實際筆數（`detect.py` 產出）：ftv 341、tvbs 424、ebc 450、cts 420，合計 **1635 筆**。

| 設定 | 推算依據 | 單一頻道總時間 | 4 頻道並行總時間（以最多筆的 ebc 為瓶頸） |
|---|---|---|---|

## 9. 建議

1. **採用 optimized 設定**：速度、穩定性都大幅提升，`think:false` 是最關鍵的修正（不只是加速，還解決了 baseline 38.5% 的失敗率）。
2. **準確度有一定代價，建議加一道覆核機制**：例如同一個「則」在穩定期間通常會被 heartbeat 或相鄰 event 重複讀到好幾次，可以用**多數決**或**取信心最高的一筆**來降低單次 OCR 誤讀的影響，而不是只信任單一次 VLM 回應。
3. **cts event@331 的 HTTP 500 待觀察**：如果之後全量跑時同類錯誤重複出現在特定圖片特徵上（例如特定尺寸、特定內容），值得再深入排查；目前先依賴重試＋跳過＋記錄失敗，不會卡住整批。
4. **本機去重在這個時段效益有限**：不是機制沒做好，是這小時的新聞換標題太快；之後若有較平靜的時段或長廣告，重跑 `--estimate-only` 應該會看到更高的省下比例。
